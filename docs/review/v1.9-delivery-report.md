## 1. 高亮：三个真实成因与修复

### 成因一：亮色主题**压根没有语法高亮**（不是样式不好看，是功能缺失）

`src/editor/SourceMode.tsx` 原文：`themeComp.current.of(darkRef.current ? cmDark : [])` —— 亮色主题传入**空扩展数组**，于是亮色下落到 CodeMirror `basicSetup` 自带的默认 fallback，与暗色那套硬编码 GitHub Dark **完全不一致**。

| | 修复前 | 修复后 |
|---|---|---|
| 亮色源码模式 | 22 个 span / **18 个有色** | 63 个 span / **63 个有色** |
| 暗色源码模式 | 19 个 span / 17 个有色 | 63 个 span / 49 个有色（暗色本就靠底色对比，前景色与父级相同属正常） |

修复：新增 `src/editor/cm-theme.ts`，给出**成对**的 `cmLight` / `cmDark`，共用同一批 Markdown token 规则，各自适配底色。

### 成因二：代码块在**两套主题下都是硬编码深底**

`src/styles.css` 原文 `.code-block { background: #282c34 }` —— 亮色页面里嵌一块 atom-one-dark 深色（实测 `barBg/codeBg = rgb(40,44,52)`，两套主题完全相同）。

修复：把 highlight.js 的语义 class（`.hljs-keyword` / `.hljs-string` / …）**映射到项目令牌**，两套主题各自协调，且**零新增依赖**（hljs 官方主题 CSS 是全局 class 样式，亮暗两套不能同时引而不加作用域限定；本地缓存里虽有全套主题 CSS，但直接引会与项目的令牌体系脱节）。

实测：亮色底 `rgb(246,248,250)` / 暗色底 `rgb(27,30,35)`。

### 成因三：六种 Markdown 标记符**共用一个 tag**，原理上无法分别着色

`@lezer/markdown` 的 `defineTags` 把 `HeaderMark` / `QuoteMark` / `ListMark` / `LinkMark` / `EmphasisMark` / `CodeMark` **全部映射到 `tags.processingInstruction`** —— 这是「高亮看起来乱」的真正根因。

实测两条路径：
- **HighlightStyle 不可行**：6 种标记符全部拿到同一个 class `ͼo`（`Tag.define({HeaderMark:true})` 也不行 —— 节点名落在 `set` 里，`highlightTags()` 取不到）。
- **可行路径 = `syntaxTree` + `Decoration.mark`**：6 种标记符拿到各自独立的 class（`mw-HeaderMark` / `mw-QuoteMark` / `mw-ListMark` / `mw-EmphasisMark` / `mw-CodeMark` / `mw-LinkMark`）。这与本项目 `src/editor/code-block.ts` 已有的 Decoration 范式一致，不是新机制。

### 附带修复
- **源码模式行号与代码间约 120px 的断裂空白** → 改为「编辑器整体居中」，行号紧贴代码，**间隙 0px**。
- **两模式正文行宽不一致**（源码 820px vs 富文本 780px）→ 统一为 **780px**（860 盒宽 − 80 内边距），切换模式文字不再重排。
- **查找高亮与选区配色**：普通命中「淡琥珀」`#fff3b0`、当前命中「浓琥珀」`#ffb020` + 深棕描边 `#7a3b00`（同色系靠颜色区分不够，描边是第二重视觉线索；描边色对**高亮底色**须 ≥ 3:1 —— 对 `#ffb020` = 4.68:1、对暗色主题的 `#f59e0b` = 3.99:1）；暗色下当前命中改为**橙** `#f59e0b` 与普通命中拉开色相；选区亮 `#cfe2ff` / 暗 `#2f5480`。

## 1c. 后续修订（2026-11-25）：光标/激活样式重做 + 头部按钮功能排查

用户反馈两条：**「编辑器中的光标和激活样式太丑了」** 与 **「头部的功能按钮功能有问题，检查所有功能按钮，尤其是关闭按钮，关闭按钮的功能无法使用」**。

### 关闭按钮失效 —— 真 bug，根因是 Tauri 权限

| 环节 | 事实 |
|---|---|
| 能力配置 | `src-tauri/capabilities/default.json` 只声明了 `core:window:allow-close`，**没有 `allow-destroy`** |
| 关闭流程 | `close()`（已授权）→ 触发 closeRequested → `preventDefault()` → flush → **`destroy()`**（未授权，被 ACL 拒绝） |
| 静默失败 | `void promise` 把 rejection 吞掉 → **窗口永不关闭** |
| 后果放大 | 应用是 `decorations: false`（自绘标题栏），× 是**唯一的**关闭入口 → 完全无法退出 |

**修法（三层）**：
1. 能力配置补 `core:window:allow-destroy`；
2. 关闭流程改为**幂等的「二次 close」**：第一次请求拦截并 flush，随后再次 close（此时不再拦截，走正常关闭）→ 正常路径只依赖已授权的 `allow-close`；`destroy` 仅作兜底；
3. flush 期间再次点关闭**继续拦截**（否则会在落盘前关窗，丢未保存内容）。

同时给所有窗口命令套上 `runWinCmd()`：失败弹 toast，不再静默吞异常 —— 这正是当初「无从判断是应用坏了还是没点对」的根源。

### 头部按钮全量体检（`.workbuddy/review/titlebar-probe.cjs`，真实浏览器，25 项全通过）

逐个点击并断言**可观测效果**：新建（标签页 +1）、保存（mock 文件系统内容更新）、最近（面板弹出）、主题（主题切换）、设置（面板打开）、源码⇄所见即所得、随航；另含 4 项权限静态检查与 1 项「窗口命令不得静默吞异常」的源码守卫。

体检中另外查出并修掉：
- **窄窗下按钮会整块消失**：旧实现在 ≤1100px 隐藏「打开 / 文件夹 / 最近 / 主题 / 设置」—— 打开文件与文件夹是主流程入口，窄窗下反而用不了。改为**只隐藏文字、保留图标与功能**（`.tb-label`），并给每个按钮补稳定的 `aria-label`（可见文字会变的按钮尤其需要）。
- **模式按钮漏了 `aria-label`**（其余按钮都补了）。

### 光标与激活样式 —— 从「实测几何」倒推的设计

| 项 | 修改前 | 修改后 |
|---|---|---|
| 光标颜色 | `caret-color: rgb(31,41,55)`（默认深灰，像没配过） | **`var(--accent)`** —— 亮色 `#0a754d`（5.73:1）、暗色 `#34d399`（7.99:1）；源码模式同步 |
| 焦点指示 | `box-shadow: inset 3px 0 0 0` → 落在编辑区盒子左缘 | **伪元素画的 2px 渐隐线**，`left: 40px`（= 正文左内边距），上浓下淡 |

为什么上一版还是不对：实测几何显示焦点线在 **x=332**、正文在 **x=372** —— 那条线孤零零挂在正文左侧 40px 的空白里，与内容脱节。整框 `inset 0 0 0 2px` 更糟（把整个写作面框成「一个输入框」）。

**第三轮修订（用户追问「这个绿色的边框是什么？」）**：那条线之所以**一直在**，是因为用了 `:focus-visible` —— 实测 Chrome 对 contenteditable 的 `:focus-visible` 启发式是**总是匹配**（鼠标点击进入时 `matches(":focus-visible") === true`），于是本该「键盘用户才看到」的焦点指示变成了画布上的**常驻元素**。
改为**自建输入模态追踪**（`src/editor/focus-indicator.ts`）：导航类按键 → 键盘模态；指针按下 → 指针模态；编辑区获焦时按当时模态决定是否显示指示线，焦点已在区内时鼠标点击立即撤掉。
结果：**鼠标点击进入 → 画布完全干净（无绿线）**；键盘 Tab 进入 → 出现 2px 渐隐线（WCAG 2.4.7 仍满足）。新增闸门 `focus-mode-probe.cjs`（4 项）覆盖这四种组合。

## 1d. 后续修订（2026-11-25 下午）：自定义主题改为「基色派生 + 深浅自动配比」

用户诉求：**「自定义主题的风格，应该同时改变整个软件，而不是只修改编辑器的主题；而且主题的配色也要根据深色或浅色系进行配比」**。

### 问题根因

| 现象 | 根因 |
|---|---|
| 只改了编辑器 | 主题文件是**裸 CSS 注入**，应用有 **58 个颜色令牌**；主题只声明 4 个变量时，其余 54 个仍是内置默认 —— 视觉上「只有编辑器变了」 |
| 深浅两套配比全乱 | 注入的是无条件的 `:root {...}`，与内置的 `[data-theme="dark"] {...}` **同特异度且更靠后** → 深色模式下被浅色值整体盖掉 |

### 现在的约定

**① 基色派生（推荐）** —— 只写 3~5 个基色，系统推导出**全部**令牌：
```css
:root {
  --mw-base-bg: #fbf1d8;        /* 主底色（浅色模式） */
  --mw-base-fg: #4a4235;        /* 主文字色（不给则由底色派生） */
  --mw-base-accent: #b58900;    /* 强调色 */
}
/* 可选：显式给暗色基色；不给则由系统自动派生（压暗底色、提亮强调色） */
[data-theme="dark"] { --mw-base-bg: #241f18; --mw-base-fg: #e8dfd0; --mw-base-accent: #e0b155; }
```

派生规则：
- **中性色**（表面 / 边框 / 文字）取基色的**色相**，饱和度压低，明度按模式排布；
- **强调色**在浅色模式压暗、深色模式提亮，并**自动保证**与正文底色对比度 ≥ 4.5:1；
- **语义色**（危险 / 警告 / 差异 / 代码高亮 / 标记符）保留内置值 —— 它们承载语义，强行同色相会丢失区分度，主题文件仍可显式覆盖。

**② 逐个令牌覆盖（旧写法，完全兼容）** —— 直接写完整 CSS 变量，行为与从前一致。判定依据：文件里出现 `--mw-base-*` 走 ①，否则原样注入。

注入用 `:root:not([data-theme="dark"])` 与 `[data-theme="dark"]` 两条规则 —— 前者特异度更高但**不匹配暗色模式**，因此不依赖样式表先后顺序，深浅两套不会互相盖错。

实现：`src/theme/palette.ts`（颜色运算 + 派生）、`src/theme/apply.ts`（解析与应用）。

### 实测（`theme-probe.cjs`，真实浏览器 23 项全通过）

- **整个软件都变了**：标题栏 / 侧栏 / 状态栏 / 编辑区 / 标题栏按钮 / 代码块 / 行内代码 —— 逐项与无主题基线比对，全部不同 ✓
- **深浅配比正确**：暗色底色更暗（亮度 0.888 → 0.047）、暗色文字更亮、**暗色强调色更亮**（`#876600` → `#ffdb6b`）、标题栏 / 侧栏 / 状态栏 / 代码块全部随模式变化 ✓
- **对比度自动兜底**：浅色 正文 8.84:1 / 次要 4.56:1 / 强调 4.77:1；暗色 正文 7.07:1 / 次要 4.52:1 / 强调 8.05:1 —— 全部 ≥ 4.5:1 ✓
- **旧写法兼容**：逐个令牌覆盖仍生效，且其 `[data-theme="dark"]` 块能盖过应用内置的暗色块 ✓

改为读取**本机更新清单** `%APPDATA%/MWTyper/update-manifest.json`：
```json
{ "version": "0.2.0", "url": "https://…/MWTyper-0.2.0-setup.exe", "notes": "…", "publishedAt": "2026-11-25" }
```
- 版本更高 → 显示新版本号、更新说明、发布日期、复制下载链接 / 打开下载页；
- 版本不更高 → 「当前已是最新版本」；
- **没有清单 → 如实说明「未内置在线更新源」并给出路径与格式示例，绝不谎称检查过或已是最新**。

检查逻辑与将来接在线源完全一致，只是把「取清单」从网络换成本地文件。

Rust 侧新增 3 个命令（`app_info` / `read_update_manifest` / `update_manifest_path`）+ 3 个单测；构建时间由 `build.rs` 注入。

## 1f. 后续修订（2026-11-25 晚）：标题栏重组 —— 顺带挖出一个 P0 数据丢失缺陷

用户诉求：**「重新整合菜单栏」**。

### 重组前的结构性问题
右侧挤了 **12 个控件**（新建/打开/文件夹/保存/最近/主题/帮助/设置/源码/随航 + 3 个窗口键），**视觉权重完全相同**、看不出层级；且「⇄ 源码」与「⧉ 随航」两个按钮**表达不清三态关系** —— 用户看不出当前在哪一态，也不知道点哪个能到哪一态。

### 重组后
```
[☰] 文件名 ●          [＋新建] [▣保存] [所见即所得|源码|随航]  [◷最近] [?帮助] [⋯更多] [⚙设置]   [─ □ ×]
```
- **保存** 唯一实心主按钮；**新建/最近/帮助/更多/设置** 为 ghost（透明底、hover 才显形）→ 默认态安静。
- **模式改用三分段控件**，当前态高亮、可直接点选；`role="radiogroup"`，方向键可切。
- **低频操作收进「⋯ 更多」**，按**语义类别**分组（文件 / 视图 / 帮助）。
- **「打开文件夹」移到侧栏「文件」页工具栏**（工作区操作，语义上不属于标题栏），且**未打开工作区时也在**。

### 顺带挖出的 P0 数据丢失缺陷
探针在验证「新建 → 切回标签 → 打字 → 保存」时发现：**切回标签后敲一个字符，整篇文档被替换成那个字符**（实测「标题正文内容。」→「X」）。

根因：`setContent` / `replaceWith(0, size, …)` 是**整篇替换**，ProseMirror 把选区映射成**整个新文档**；若编辑器仍持有焦点（外部文件变更触发重载、快照恢复、从随航切回），用户下一个按键就抹掉全文。

修复：新增 `collapseSelection(ed)`（`src/editor/caret.ts`），所有整篇替换之后把选区收成**折叠光标**。落点三处：`loadBuffer`（切标签/装载）、`syncPreview`（随航预览同步）、`toWysiwyg`（随航切回）。

**回归守卫已收紧**：`titlebar-probe` 的 T2b 原来只查 `saved.includes("X")` —— 整篇被替换成 "X" 也算「包含 X」，会放过这个缺陷；现改为**同时确认原文还在**。

## 1i. 后续修订（2026-11-25 上午）：专注模式 / 打字机模式「无效」

用户反馈：**「专注模式和打字机模式无效」**。

### 实测定位：三处具体问题

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | **从设置面板勾选专注模式 → 当前段落没有高亮**（段落变淡了，但「正在写的那段」不突出 → 看起来像没生效） | 「当前段落高亮」由 PM 插件在**事务**里重算；设置面板改的是 `settings`，**不产生事务** → 插件永远不重算。F8 路径有显式 dispatch，所以只有面板路径失效 | 监听 `settings.focus_mode` 变化，补一次 meta 事务让插件重算 |
| 2 | **从设置面板勾选打字机模式 → 不滚动** | 打字机靠 `lastTwPos` 去重（光标位置没变就不重复滚）；面板路径没像 `toggleTypewriter` 那样重置它 → 开启时恰好被去重挡掉 | effect 内记录「刚开启」沿（`twWasOnRef`），刚开启强制滚动一次 |
| 3 | **开启后状态栏毫无指示** | 状态栏只显示编辑模式 → 开了却「看不见开了」，进一步坐实「无效」的观感 | 状态栏新增「专注」「打字机」标记 |

### 顺带修掉一个被 QA 基线抓到的连带缺陷
第 1 项补的事务若不带 `preventUpdate`，会**唤醒 PM 的 `appendTransaction` 链**（trailing-node 等规范化插件 append 一个 docChanged 事务）→ tiptap `emit('update')` → `markChanged` → **新建的空白草稿被误标「未保存」**。
这个缺陷是被 `spikes/qa4-probe.ts` 的 P3-9 / P3-12 抓到的（我先停用新 effect 做了因果实验，确认 121/121 恢复，才定位到元凶）。
修法：事务带 `preventUpdate`（tiptap 自己的 `setContent` 也是 `setMeta('preventUpdate', !emitUpdate)`）—— 这类事务只是让插件重算装饰，不是内容变更。

### 另外把专注模式的「当前段落」做得更醒目
除恢复不透明外加一条**左侧强调线**（`box-shadow: inset 2px 0 0 0 var(--accent)`）—— 只靠 opacity 0.65 ↔ 1 的差别太细微；用 box-shadow 而非 padding，避免文字横向跳动。

## 1j. 后续修订（2026-11-25 中午）：窗口按钮图标错位

用户反馈：**「这三个图标的样式有错位」**（截图里最小化/最大化/关闭三个窗口按钮）。

**修复**：改为**内联 SVG** —— 统一 `viewBox="0 0 12 12"`、`stroke-width: 1.3`、`stroke-linecap/linejoin: round`；按钮固定 30×26 并用 flex 严格居中。

## 2. 随航编辑（第三种模式 `split`）

| 能力 | 实现 |
|---|---|
| 布局 | 左源码（CodeMirror）／右实时预览（**复用现有富文本实例做只读渲染**），CSS Grid 三栏：工具条横跨两栏 + 源码 + 分隔条 + 预览 |
| 事实源 | `split` 下 **CodeMirror 是事实源**，富文本退化为只读预览（`setEditable(false)`）；保存的是源码，不是预览 |

| 滚动联动 | 按滚动比例映射，两侧互驱；**单向锁 + 120ms 冷却**防止正反馈抖动 |

| 入口 | 标题栏「随航」按钮 + `Ctrl+Shift+/`；「⇄」按钮在随航时归到「所见即所得」一侧 |

### 实施过程中踩到并修掉的 3 个真 bug
1. **⇄ 按钮在随航下走错分支** —— `toggleMode` 原本只认 `source`，随航时会被当成「还没进源码」又进一次源码。改为「非所见即所得即回所见即所得」。
2. **随航退出后编辑器仍是只读** —— `toSource` 的随航分支忘了恢复 `setEditable(true)`，切回去「能看不能改」。

## 4. 已知限制与仍需注意

1. **源码模式的删除线没有专属着色** —— `@codemirror/lang-markdown@6.5.2` 的 `markdown()` **没有 `extensions` 参数、也不导出 `GFM`**，CommonMark 不认 GFM 删除线，`~~删除线~~` 在源码侧不会被解析成 strikethrough tag。删除线的高亮只在所见即所得侧成立。要补需自定义 parser，代价与收益需另评估。
2. **随航退出到所见即所得时，富文本实例的 undo 栈不干净** —— 预览同步虽已带 `addToHistory:false`，但模式切换本身的 `setContent` 会进历史（这是上一轮就有的行为，未在本轮改变）。
3. **`split_ratio` 只影响随航模式的分栏**，不影响其它模式。
4. **随航的预览不是所见即所得的完整等价物** —— 它复用的是同一个 tiptap 实例，因此渲染结果一致；但预览是**只读**的（表格工具栏、查找条等编辑态 UI 在随航下不出现）。
5. **真实 Tauri 窗口观感仍需人工确认一次**（原生剪贴板/拖拽、原生对话框、WebView2 打印对话框）—— 无头环境无法复现。

## 6. 关于团队协作的说明（透明起见）

本轮按 SOP 建了团队并派了产品经理与架构师两个角色。**子代理的模型请求在本会话中反复挂起**（实测：读取大文件或长输出的子代理几乎必然停在工具调用之后；一个只写 2 字节文件、不读文件的最小子代理则秒完成），因此：

- **产品经理角色三次派发均未交付** → 产品范围改由主理人依据**用户已通过交互确认的两个决策**（随航 = 源码｜预览并排；高亮改造覆盖四项）直接固化；
- **架构师角色最终产出了 `v1.9-palette.json`，其配色与主理人独立实现并实测通过的色值完全一致**（同一组 hex，构成有效的交叉验证），设计文档由主理人承接产出；
- **工程实现与验收由主理人直接完成**，全部结论都有实测脚本与真实浏览器证据支撑，未采信任何未经验证的转述。

这是工具限制下的处置，不影响交付质量，但**流程上确实偏离了「成员产出、主理人汇编」的理想形态**，如实记录在此。
